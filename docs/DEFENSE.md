# Defense walkthrough

Use a prepared test account and realistic illustrative inputs. Each member explains the assigned area in TEAM.md, but everyone must be able to trace the full application.

1. Landing → starting point → onboarding: select exactly five interests and traits. Explain external Zod schemas, RHF, field errors and profile matching.
2. Explore catalog: search a topic and sort by score/capital/time. Explain the 40/25/20/15 weights and why a score is not a success prediction.
3. Create a plan, edit its name, reopen it. Explain React → Axios → Express → Mongoose → MongoDB and owner-scoped access.
4. Open a section: Zee starts, asks short questions, drafts an essay. Revise, open history and restore. Explain that review status resets. If Gemini is unavailable, say so and demonstrate a prepared draft without pretending it was generated live.
5. Money lab: capital 100,000; price 150; variable cost 60; monthly sales 100; oven 20,000 startup; rent 5,000 monthly. Show startup 20,000, revenue 15,000, expenses 11,000, profit 4,000, break-even 56 sales. Compare 70/100/130 sales. Set price equal to variable cost to demonstrate no finite break-even.
6. Add an invalid negative cost or blank name to show validation, then a valid cost. Edit it. Confirm deletion only on disposable test data. Show recalculated totals.
7. Launch checklist: create a task due yesterday, then mark complete. Today is not overdue; completed tasks are excluded from overdue counts. Empty checklist is 0%, not 100%.
8. Show an unknown API path returning JSON 404 and malformed input returning JSON 400. Explain why another account cannot access this plan.
9. Review/export: explain draft vs reviewed, executive-summary lock and assumptions. Download a PDF and open it before presenting.
10. With live Atlas connected, refresh and sign back in to demonstrate stored data; inspect the matching record in Atlas. An ephemeral QA database is not evidence of Atlas persistence.

Pre-presentation: run build/lint/tests, check Gemini quota/model, Atlas access and network, record actual screenshots, confirm professor's repository instructions, verify every member's authentic commits and rehearse individual questions.
